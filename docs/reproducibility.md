# Reproducibility and paper coverage

This document maps the included workflows to the paper and distinguishes
paper-reported facts from reconstructed configuration details. A launchable
training config is not a reproduced result: no weights, datasets, training logs,
or evaluation outputs are included. The included workflows have not been
validated through a full GPU training run.

## Reported facts and reconstructed choices

The following are stated in the paper and reflected in the retained base config
and method matrix: Qwen3-8B base-to-RL training on DeepMath-Hard; LoRA
`alpha=32`, dropout 0, all-linear targeting; DoRA ranks 8/16/32/64; QuanTA d=3
`[16,16,16]` and d=4 `[16,8,8,4]`; G=8 for the main protocol; completion
batches 64/128/256 with 674/337/168 optimizer updates; four H100 GPUs for the
reported DDP setup; BF16; fused AdamW; one epoch; learning rate 1e-5; cosine
decay, warmup ratio 0.1, minimum LR ratio 0.15; beta 0; Dr. GRPO; and the
DeepMath-Hard row count 5,399. The matrix additionally exposes QuanTA targets
for all linear projections, no value projection, and no key/value projections.

The paper does **not** report per-rank `micro_batch_size` or its gradient
accumulation setting. The included base uses `micro_batch_size: 2` as a
reconstructed configuration choice; the materializer derives
accumulation as:

```text
completion_batch / (local_process_count × per-rank micro_batch_size)
```

For the documented one-node, four-process setting, this yields accumulation 8,
16, or 32 for completion batches 64, 128, or 256. This is an implementation
reconstruction, not a paper-verified Axolotl effective-batch equivalence. The
selected runtime must be checked to ensure its GRPO batching semantics match
the intended completion/prompt accounting before claiming an exact
reproduction.

### Reward implementation difference

Appendix A.3.2 describes the format reward as a weighted set of additive
conditions. The `src/rewards.py` function
`strict_format_reward_shaped_4_empty` is not an exact transcription of that
description, and the config's reward weights must not be taken as evidence that
all paper-reported reward weights are reflected exactly. Specific differences
include:

- Any `<think>` opening tag incurs an additional `-0.2`, including an otherwise
  valid single reasoning block; the paper's listed conditions do not describe
  this penalty.
- More than one `</think>` incurs `-0.1`.
- Repetition has separate implementation checks: repeated lines can incur
  `-0.5`, while a repeated-trigram ratio below `0.5` incurs `-0.4`; these do
  not match the paper's single repetition description/weight of `-0.5`.
- Early-return branches change which terms are accumulated: a detected
  hallucinated turn returns `-0.75` immediately; empty reasoning returns before
  answer/repetition checks; repeated lines return before trigram and answer
  checks. Thus the behavior is not simply the paper's additive list.

These differences mean the included format reward should not be treated as an
exact reproduction of Appendix A.3.2.

### Group-size reconstruction

The optional `run_group_size_reconstruction.sh` preserves the existing
eight-prompt-groups-per-update geometry: G=4 uses 32 completions/update, and
G=16 uses 128. With 5,399 prompts, each gives 674 full updates and drops seven
rows at the epoch boundary. The paper says the remaining protocol is held fixed,
but these source configurations also change completion batch as G changes.
Therefore this is not a controlled G-only sweep and must not be represented as
the paper's exact group-size experiment. Nondefault-G resolved outputs use a
`/g-<G>/` directory component;
the default G=8 output path is unchanged. The materializer records the selected
batch, group size, microbatch, accumulation, step count, and dropped-row count
in provenance JSON.

For configurations using the materializer, the count arithmetic is
`unique_prompts = completion_batch / G` and
`optimizer_steps = floor(5399 / unique_prompts)`. It yields 674/337/168 updates
for the paper's main completion batches at G=8. This arithmetic is explicit;
whether the runtime executes one optimizer update over exactly that many
unique prompts depends on Axolotl/TRL batching behavior and has not been verified.

QuanTA is not native Axolotl adapter dispatch in the pinned runtime. The
included `src/quanta_axolotl.py` supplies config registration, adapter loading,
and vLLM synchronization against the pinned QuanTA fork. That integration is
implementation support reconstructed from source, not a detailed integration
specification in the paper. It deliberately rejects FSDP and ZeRO-3 for this
trainer; the paper reports DDP.

## Data and evaluation gaps

- DeepMath-Hard curation is not packaged. Supply the paper's already-filtered
  5,399-row train split with the expected columns. `rewards.deepmath_transform`
  transforms a row; it does not apply the ≥8.5 difficulty filter or prove that
  a supplied dataset matches the paper's split.
- Skywork-Hard needs the `train-math-deepscaler` split and the paper's
  DeepSeek-R1-Distill-Qwen-32B `model_difficulty ≥13` selection. No such
  filtering or evaluation pipeline is included.
- Enigmata requires the 35 shared tasks and the paper's task/difficulty
  stratification to 2,930 easy / 3,381 medium / 3,689 hard examples, plus the
  official evaluation set. None of these files or transforms are included.
- MATH and Skywork-Hard scoring/evaluation, Enigmata official evaluation, and
  AIME 2025–2026 Avg@32 sampling/scoring are not included. The presence of
  general reward transforms in `src/rewards.py` is not evidence of those
  benchmark pipelines.
- `requirements-analysis.txt` is an intentionally unpinned optional plotting
  add-on for a separately managed analysis environment. It only lists
  `matplotlib` and `seaborn`; prerequisites such as PyTorch, NumPy, pandas,
  SciPy, and safetensors must already be present. It is not the paper runtime
  lock, and its installation or plotting compatibility has not been validated.
- Checkpoint analysis requires retained training artifacts and score labels in
  the format consumed by `deepmath_spectral.discover_runs`. No scores or
  checkpoint conversion is supplied. The analysis helper discovers flat,
  specially named run directories; it is not directly wired to the training
  launcher's `run-id/seed/batch` output hierarchy, so staging may be needed.
  Frozen SVD analysis requires all three model checkpoints and considerable
  host RAM.

## Environment freeze and verification boundaries

The paper's Table 9 reports Ubuntu 24.04, CUDA driver 12.8.0, BF16,
PyTorch 2.9.0 with custom torchao 0.13.0, Axolotl 0.13.0, vLLM 0.11.1,
FlashAttention 2.8.3, xFormers 0.0.33, and DDP on 4×H100 64 GB. The included
container definition uses a CUDA 12.8.1 development base; its dependency lock
pins Axolotl `0.13.0.dev0` and xFormers `0.0.33.post1`, and its build-time
version assertion checks torchao `0.13.0+cu128`. These are not identical
version strings to Table 9. The paper does not state a TRL version; the runtime
lock pins TRL 0.25.1. This tree preserves the available container freeze rather
than claiming it is an exact paper environment or a currently resolvable
generic `pip freeze`.

Container builds, package resolution, GPU execution, model loading, and full
training have not been validated for this release. Offline config/unit checks can
validate local structure but cannot resolve the environment differences or
certify paper metrics. In particular, the selected config is the reported DDP
path, not an FSDP substitute; full-parameter FFT at 8B scale may exceed a
single H100's memory under ordinary replicated DDP. The optional analysis
dependencies and their compatibility with separately managed environments are
also unvalidated.
